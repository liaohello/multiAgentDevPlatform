## 2. 关键发现（按影响排序）

### F01 · P1：迟到验收可以覆盖用户取消，阻塞结论也可能被判完成

位置：[controller.py:1094](../../backend/app/controller.py:1094)，关键完成分支在 [1120](../../backend/app/controller.py:1120)。

应用审阅时主要检查逐项 PASS、当前快照及两个版本，没有在提交时要求 Goal/Run 仍处于允许状态，也没有将 `overall=BLOCKED` / `next_action=request_user` 或失败执行结果作为完成阻碍。

受控复现一：在审阅已捕获旧 Goal 信息后取消任务，再应用迟到的逐项 PASS，实际状态从 `CANCELLED` 变成 `COMPLETED`。

受控复现二：现有程序验证退出码为 1、Result 为 failed，注入“逐项 PASS，但 overall BLOCKED、请求用户决定”的结构化结果，仍变成 COMPLETED。

影响：取消和阻塞不能可靠保护任务终态，模型不一致输出可能覆盖用户意图或失败事实。已有快照漂移测试不足以证明整个完成门禁。

修复验收：应用前在同一状态事务核对当前 Goal/Run/Review、目标/计划/验收版本和允许转换；迟到或冲突结果只归档，不改变取消状态。失败的必需验证、BLOCKED/UNKNOWN 结论不得直接完成；旧 Run 的审阅不能完成新 Run 的交付。

### F02 · P1：Wiki 目录边界可越过，索引正文会读错文件

位置：[wiki.py:120](../../backend/app/wiki.py:120)、[read_body:167](../../backend/app/wiki.py:167)、[read_workspace_path:188](../../backend/app/wiki.py:188)。

目录授权使用字符串 `startswith`。注册根目录为 `scope` 时，其兄弟目录 `scope-other` 同样满足字符串前缀；通过 `../scope-other/note.md` 可读到本不属于该工作目录的文件。检查只涉及本轮创建的无敏感测试文件。

扫描保存的是相对注册 Workspace 的路径，但 `read_body` 又通过应用项目根解析。外部测试 Workspace 的 `README.md` 索引，实际返回 agentProj 自身的 README。若项目根不存在同名文件，也会出现错误的不存在结果。

另外，排除规则检查绝对路径的所有祖先。默认演示 Workspace 本身在 `.agentproj/` 下，所以所有演示 Markdown 被跳过，扫描结果为 0，即使 README 明确存在。

修复验收：使用真实路径包含关系，按索引来源在 Workspace 或授权导入存储中解析并重新校验边界；排除规则只针对 Workspace 内相对路径。补测同前缀兄弟目录、同名文件的不同 Workspace、默认演示目录，以及符号链接/Windows junction 的实际可用情况。

### F03 · P1：Token 基线未持久化，重启续接会重复累计

位置：[budget.py:114](../../backend/app/budget.py:114)；Provider 归属还见 [controller.py:415](../../backend/app/controller.py:415)。

累计线程基线只保存在 `Budget._thread_totals` 内存。首次累计 100，重建 Budget 后收到累计 150，新增值被算为 150，账本总量成为 **250**，应为 **150**。全局快照去重键无法纠正这个新快照的重复前缀。

现有“重启锁仍关闭”用例验证的是预算锁，没有验证重启后真实线程继续结算。输入/输出细分也直接使用累计值，没有与 total 的增量语义统一；真实 Worker 的 Provider 在回调中被硬编码为 openai。用量回调异常被忽略，需要补充可见的未知/待结算处理。

修复验收：持久保存按线程、计量周期和调用归属的基线，处理重启、重置、重复和迟到；total 与细分一致；读取实际 Provider。计量失效不能静默表现为零消耗并无限续轮。补测 100→重启→150 仍累计 150。

### F04 · P1：超时与恢复没有保证原生执行已停止

位置：[codex_appserver.py:357](../../backend/app/adapters/codex_appserver.py:357)、[controller.py:1313](../../backend/app/controller.py:1313)。

Adapter 超时后直接退出读取循环并清空活动 Turn ID，没有发送中断或确认原生执行结束。受控存活 Stub 只收到 `turn/start`，未收到 `turn/interrupt`；本地返回 timeout，但原生端仍被标为存活。

重启恢复把所有遗留执行直接标成 INTERRUPTED，备注又承认进程归属未知；用户恢复后新的 Run 可进入 QUEUED，没有先验证旧进程是否停止。当前 WSL 残留检查函数没有接入该控制路径。

影响：本地 Run 结束不等于原生 Worker 停止，可能导致后台继续消耗或修改文件，而新的执行又占用同一目录。原生主动中断的成功证据不能覆盖超时、断线与重启场景。

修复验收：超时请求中断并有界确认，必要时只清理已确认归属的进程；无法确认时保持 UNKNOWN 与写入阻碍。恢复前核对运行身份，不把未知状态直接释放为可写槽。用真实短时可控进程验证，模拟计时器只能作为补充。

### F05 · P1：多任务计划没有任务推进，始终选第一项

位置：[controller.py:645](../../backend/app/controller.py:645)。

任务选择固定为 `task_row = tasks[0]`，没有完成位置、依赖或下一任务选择。构造三任务计划，首个执行标记结束后再次准入，冻结的仍为 Task 1。

影响：normalize_tags 这类单任务演示可以成功，但不能证明原生规划给出的三项任务会被依次完成。真实 Worker 可能靠重规划反复绕回第一项，增加返工和成本。

修复验收：记录任务身份与完成/待办关系，按依赖推进或显式合并为一个完整任务；修复计划不能无声丢弃原未完成任务。增加至少两个实际不同交付的计划回归，验证每项进度及最终验收。

### F06 · P1：Skill 被标为已提供，但未接入实际输入，撤销后仍可显示提供

位置：[skills.py:178](../../backend/app/skills.py:178)、[controller.py:709](../../backend/app/controller.py:709)、[codex_appserver.py:313](../../backend/app/adapters/codex_appserver.py:313)。

冻结函数写入 configured/provided，但返回值没有进入执行输入；Worker Prompt 未包含所选 Skill，原生输入只有普通文本，未见所选 Skill 内容、路径或运行时根目录配置交付。状态记录发生在 Adapter 可用性检查之前。

受控复现：会话选中 token-audit 后先撤销其 allowed，再启动 Run，仍记录 configured/provided；捕获 Worker 输入没有该 Skill。现有用例主要验证数据库里的两个会话选择不同，不能证明运行时获得不同 Skill。

修复验收：发送前重新检查允许范围，将不可变内容/路径通过经验证方式交付，成功提供后再记 provided；不能提供时写未提供或 UNKNOWN。需要真正的版本内容快照，而非仅在可变记录写 frozen_at。原生严格隔离尚未完成应继续明确标注。

### F07 · P1：WSL 默认自动选择发行版的路径没有接通

位置：[wsl.py:100](../../backend/app/adapters/wsl.py:100)，尤其 [106](../../backend/app/adapters/wsl.py:106) 与 [130](../../backend/app/adapters/wsl.py:130)。

默认未配置发行版时，构造命令只有 `wsl.exe`。随后 probe 即使选到 Ubuntu，也没有更新 Adapter 命令或保存映射工作目录，路径检查因此失败。

受控 Stub 报告 WSL/Codex/路径均可用、发行版为 Ubuntu，Adapter 仍返回 FAIL。这未启动 WSL，没有尝试绕过黑名单。

影响：解除环境黑名单后，文档描述的默认配置仍可能无法工作。还需验证 Worker Provider、实际项目路径、工具和验证命令环境，不能预期直接转 PASS。

修复验收：探测结果与实际启动使用同一个发行版、执行文件和工作目录；覆盖显式/自动选择及含空格/单引号路径。真实测试要验证 DeepSeek Provider，而非仅证明发行版中任意 Codex 能启动。

## 4. 阶段评价

架构方向：可以继续。Python 单一业务调度、薄 Adapter、SQLite/文件证据以及模式分离已形成可检查的工程结构，仍适合本项目。

实现成熟度：完成可运行原型和指定样例闭环，尚未到可靠的个人日常开发工作台。主要缺口在状态/证据/进程/权限之间的真实边界，而非缺少更多框架。

证据质量：值得保留原报告的透明性，明确把真实与模拟分开。需要纠正“只有 WSL 黑名单”和“其余均完整通过”的范围；现有用例较多围绕预设 normalize_tags 路径，新增反例证明还需扩展关键场景。

用户体验：当前页面适合工程验证。用户另开的前端重设计可以推进导航、会话视图、Dashboard 与信息层级，但后端必须准确提供阻塞/未知/取消状态；不能靠前端表现修补错误的业务事实。

## 5. 下一轮建议范围

先安排一轮稳定性修复，不增加新的 Agent 框架或功能面。优先关闭 F01/F02/F03/F04，然后解决 F05/F06/F07；每项附上对应反例回归，确认原 15 项与前端构建不回退。

之后在用户允许的运行环境、已配置的 DeepSeek 和明确的小型测试预算下，完成真实 Sol→WSL Worker→Sol 全链。至少验证一次两个不同子任务的 Goal、一种真实取消/超时、重启续接后的计量及证据快照一致性。成功后重新出具 A01–A15，不直接沿用原 PASS。

前端设计可并行讨论；接口冻结和 UI 集成应以修正后的 Goal/Run/连接/预算状态为准。阶段通过条件是关键反例关闭和真实链通过，而非单独达到某个测试数量。
